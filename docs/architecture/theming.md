# Theming

### Theming (semantic, palette-agnostic)

Themes are **single config files**, not code edits. A theme is a `Theme` (`shared/theme/tokens.ts`): `{ id, name, appearance, colors, syntax }`, where `colors` fills the **26 semantic roles** in `COLOR_TOKENS` (backgrounds `--bg`/`--bg-sunken`/`--bg-deep`, surfaces `--surface`/`--surface-2`/`--surface-3`, a text-emphasis ramp `--text`/`--text-secondary`/`--text-muted`/`--text-disabled`/`--text-faint`/`--text-ghost`, and accents/status `--accent`/`--accent-soft`/`--success`/`--warning`/`--warning-soft`/`--danger`/`--info`/`--info-soft`/`--cyan`/`--magenta`/`--cursor`/`--shadow`/`--scrim`/`--input-bg`). **No component references a palette-specific swatch name** (the old `--ctp-mauve`, `--ctp-surface0`, …) — every component uses a `--<token>` semantic role or a composite `--color-*` token built on them, so a new colorscheme is purely data.

There are additionally two **optional roles** (`OPTIONAL_COLOR_TOKENS`), splitting the two jobs `accent` historically did:

- `accent-fill` — the solid accent plane behind primary actions: button fills, active segments, highlighted dialog options, checked checkboxes/toggles. Falls back to `accent`. Indicator dots and gauge fills (status/streaming dots, the context meter) deliberately stay `accent` — they *are* the signal, not a plane under one.
- `on-accent` — text/glyphs painted over `accent-fill`/`accent-soft` fills (button labels, checkmarks, toggle knobs). Falls back to `bg`, exactly what components hardcoded before the role existed (`color: var(--bg)`).

Rationale: a color tuned to be accent *text* on the page background and a color tuned to be a *fill under text* are different jobs — on a black background their luminance windows don't even overlap (AA text needs ≥4.5:1 against black; a fill taking AA light text must stay dim), so a theme must be able to set them independently. With both fallbacks, a theme that sets neither renders pixel-identically to the old single-token behavior; `applyColorScheme` always writes `--accent-fill`/`--on-accent` (theme value or fallback) so a theme switch can't leave stale values. Optional roles must stay optional: making one required would invalidate every pre-existing user theme file at load.

- **Bundled** themes: one pure-data JSON file per colorscheme under `shared/theme/themes/` (`catppuccin-{mocha,macchiato,frappe,latte}.json` + `gruvbox-material-{dark,light}.json` + `everforest-{dark,light}.json` + `glow-sticks.json` + `cendre-{hard,medium,soft}.json`), each the full `Theme` shape. `bundled.ts` imports them and parses each through `ThemeSchema` so a malformed bundled theme fails loudly at startup. They share the exact on-disk format as user themes, so a brand-new colorscheme is literally one dropped JSON file.
- **User-droppable** themes: `<userData>/themes/*.json` validated against `ThemeSchema` by `main/theme-loader.ts` (invalid/duplicate files skipped, never fatal); exposed via the `themes.listUser` IPC, with the directory path exposed via `themes.userDir` for Settings guidance; the renderer merges them over the bundled set (`theme/registry.ts`, user id wins on collision). Settings (`SettingsView`) has separate light-theme and dark-theme pickers filtered by each theme's `appearance`, storing free-string ids in `settings.lightColorScheme` and `settings.darkColorScheme`; `settings.themeMode` (`light`/`dark`/`system`) resolves which id is active. Split-theme ids use appearance-aware fallback (`resolveThemeForAppearance`): stale light ids fall back to Latte and stale dark ids fall back to Mocha, so system/light mode can never render the global dark fallback by accident.
- **Application**: `settings-store.applyColorScheme` writes each `theme.colors[role]` as `--<role>` on `:root` and calls `setShikiTheme(theme)`. Global browser text selection is themed in `renderer/src/global.css` with `accent-fill` as the highlight plane and `on-accent` for selected text, so copy/paste highlights follow the active colorscheme instead of the OS default.
- **Typography isolation**: theme files remain color/syntax-only. Persisted font settings write separate root stacks for the active session title (`--font-title`), transcript headings plus thinking (`--font-transcript-heading` / `--font-thinking`), transcript body prose (`--font-transcript-body`), and code (`--font-code`). Every user-selected reading family is one quoted CSS family followed by an app-owned fallback. The stable `--font-display` interface stack remains app-owned and continues to govern controls and the Composer; `--font-reading-heading` likewise remains the app-owned heading face for non-transcript reading surfaces such as the changelog. Changing transcript/title typography therefore cannot alter their metrics. Renderer settings writes publish optimistically but reach main in order; reading-family patches merge against the latest projected font state, and a superseded acknowledgement cannot repaint older settings over a newer choice.
- **Pi theme bridge compatibility**: `shared/theme/pi-theme.ts` mirrors pi's separate host-side role vocabulary. Pi 0.80.6 adds optional `thinkingMax`; the bridge supplies it explicitly and maps it to the semantic `magenta` role. It is appended after every pre-existing `PI_ROLES` entry rather than inserted beside `thinkingXhigh`, preserving all established host↔renderer ANSI indices (`bashMode` remains 66; `thinkingMax` is 67). Pi 0.84.0 adds optional foreground role `scrollbarThumb`, and Pi 0.84.2 adds optional foreground `searchMatchText` and background `searchMatchBg`; the public `Theme` constructor derives them from required `text`, `text`, and `selectedBg`, respectively. The bridge continues to send the complete production foreground/background maps and relies on those public fallbacks instead of adding host↔renderer ANSI indices. The SDK host builds a public local `Theme` for pi-vis-owned `TuiMainScreen` surfaces. It installs that theme globally only when Pi's public root exports a setter; otherwise it never accesses Pi's private singleton and records the decorative limitation in replicated diagnostics. Because the local semantic theme is the expected fully functional path for pi-vis-owned panels, that known non-actionable fallback does not create a warning toast on every session startup; other capability failures remain visible warnings.
- **Syntax highlighting** (`syntax`): either `{ ref: "<shiki-theme-name>" }` (reuse a Shiki-bundled TextMate theme, e.g. `catppuccin-mocha`, `nord`) or `{ inline: <TextMate theme object> }` (ship one — the Gruvbox theme uses this because no Gruvbox theme is bundled with Shiki). `shiki.ts` constructs the highlighter from the concrete object themes (the patched Catppuccin grammars) and then `loadTheme`s each string-ref theme individually with try/catch, so a single unresolvable ref (bundled or user) can never abort highlighting app-wide; it just makes that one theme fall back to the default at render. `setShikiTheme` lazy-loads user refs/inlines the same way. **UI accent tokens can't drive syntax** — this is why `syntax` is its own field, not derived from `colors`.
- **Catppuccin fidelity** (design constraint for the *Catppuccin* themes specifically): their token values stay faithful to the canonical swatches (the only sanctioned deviation is Latte's slightly-lightened surfaces, visible in `themes/catppuccin-latte.json`); depth comes from the surface ramp + hairlines + elevation, accents from translucent real swatches — never invented hues.
- **Catppuccin theming**: Four variants (latte/frappé/macchiato/mocha). Default dark theme is Mocha, default light theme is Latte, and the default mode follows the system appearance. Theme variables set via CSS custom properties.
- **Gruvbox Material / Everforest** (`themes/gruvbox-material-{dark,light}.json`, `themes/everforest-{dark,light}.json`): palette values derive from the upstream MIT-licensed sainnhe schemes (noted in `THIRD_PARTY_NOTICES.md`) and are mapped into Pi-Vis semantic roles rather than copied as component-specific swatches. These themes intentionally stay faithful to the source palettes: tests reject fabricated hex values in both UI tokens and inline syntax colors. Light-theme readability is handled by assigning upstream foreground/grey colors to the core text ramp, while canonical accent hues remain canonical even when their contrast is softer than Pi-Vis's highest-contrast themes. Gruvbox keeps its warm orange primary accent, Everforest uses green as the primary accent, and both define explicit `accent-fill`/`on-accent` pairs from source palette colors. The regression/design contract for parsing, Shiki loadability, source-palette fidelity, core text contrast, and primary-control pair presence is in `renderer/src/lib/forest-and-gruvbox-theme.test.ts`.
- **Glow Sticks** (`themes/glow-sticks.json`): OLED-first dark theme — transcript `bg`/`bg-deep` are literal `#000000` and primary text literal `#ffffff` (deep-black panels render those pixels off), with the sidebar plane (`bg-sunken`) deliberately *lighter* than the transcript. The design philosophy: non-text chrome contributes as few photons as possible, so the surface ramp is compressed to just-noticeable steps above black. Accents are verbatim swatches from the [Reasonable Colors](https://www.reasonable.work/colors/) palette built around the orange/aquamarine/indigo triad; the system's shade-3 colors share near-identical luminance (~6.2:1 on pure black), which the status/syntax roles use uniformly. `accent` (text labels, dots, syntax keywords) is the saturated orange-3 at 6.2:1 AA, while `accent-fill` is the dimmer orange-4 (4.2:1, WCAG 1.4.11 UI-component compliant) paired with a warm-white `on-accent`, so primary buttons are light-text-on-ember rather than black-on-blaze — the theme that motivated the role split. Danger is raspberry-3 (not red-3) so it can't be confused with the orange accent, and success is green-3 (hue-distinct from the aquamarine `cyan` role) so diff washes stay unambiguous. The Shiki theme is `inline` (nothing comparable ships with Shiki). Its design contract — pure-black/pure-white anchors, accent contrast floors, ramp ordering, on-accent pairings — is locked by `renderer/src/lib/glow-sticks-theme.test.ts`.
- **Cendre** (`themes/cendre-{hard,medium,soft}.json`): the three dark variants preserve Cendre's premise that the pigments are the identity and only the ash-bed ground moves. As on Cendre's site and in Everforest Dark, the transcript/diff ground uses `g0`, the sidebar and diff rails use the lighter `g1`, raised cards/dropdowns use `g2`, hover/structural separation uses `g3`, and the strongest text-bearing surface uses `g4`; do not reverse or collapse that hierarchy merely because the app's semantic sidebar token is named `bg-sunken`. `g5` is intentionally not assigned to a text-bearing app plane: at Soft depth, primary ink on `g5` is only 4.38:1, which would create a new contrast exception not allowed by Cendre's stated rules. Hard, Medium, and Soft therefore share ink, five syntax pigments, semantic diagnostics, and all 33 upstream TextMate rules; only their ground-derived UI roles, per-depth on-accent foreground, and Shiki editor ground values differ. Each modal scrim uses its depth's published `g-1` channels at 70% opacity so the shared backdrop blur remains visible rather than replacing the app with an opaque ground. Semantic status roles stay in Cendre's diagnostic family (`warning-soft` is warning amber, not the brass syntax/search pigment), while the primary/soft UI accents remain ember/brass. The inline Shiki definitions are faithful conversions of Cendre's generated `extras/bat/*.tmTheme` files, including comments, literals, escapes/regex, names, parameters/properties, markup, diff, invalid, and deprecated scopes. Every color literal comes from Cendre's published/generated palettes; Pi-Vis does not interpolate replacement colors. Contrast is likewise preserved rather than “corrected”: comments intentionally remain below 4.5:1 at all depths (3.32, 3.14, and 2.94), and Soft deliberately retains the documented sub-4.5 frost/type and error colors. Ordinary UI copy uses the stronger ink levels, while source-specified quiet/comment roles stay quiet. This palette, depth-invariance, complete-Shiki, loadability, and contrast contract is locked by `renderer/src/lib/cendre-theme.test.ts`.
