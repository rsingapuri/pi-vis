# Runtime services

Read this when changing browser preview, auth/login, embedded PTY, the pinned pi runtime, app update checks, subprocess environment, or native runtime dependencies.

- **Browser preview**: `npm run dev:renderer` loads `preview-stub.ts` which stubs `window.pivis` with a demo session and canned responses including streamed agent output.
- **Auth / subprocess env**: API keys are stored in `~/.pi/agent/auth.json` using `proper-lockfile` for mutual exclusion with pi's token-refresh writes. GUI launches recover the user's environment once via `$SHELL -ilc env`; after child creation, the five-second, one-MiB capture is single-flight, uses best-effort process-tree termination, and tears down its local capture pipes at the deadline. `getSubprocessEnv()` combines `process.env` + login-shell env for consistent subprocess PATH across git, PTY, and node/pi spawns. System-Node discovery reuses that environment for a bounded PATH lookup and version probe within one shared five-second budget rather than invoking another login shell. Pi session spawns additionally merge `settings.piEnv` (advanced Settings UI, one `KEY=value` per line; applies on new spawn or `/reload`) after the login-shell env and before Pi-Vis-owned `PIVIS_*` controls. The account surface uses that same sanitized, Settings-wins environment and republishes status after every committed `piEnv` change. Its provider IDs, names, OAuth capabilities, and API-key variables match the complete pinned 1.0.0 built-in registry; compound Cloudflare, Vertex, Bedrock, and Anthropic sources are reported only when Pi would consider them configured. Stored credentials retain precedence, and Anthropic environment status follows request resolution exactly: bearer token, OAuth token, API key, then the complete rule/organization/identity-token-file workload-identity configuration. Only redacted source labels cross IPC; environment and stored credential values never do. The runtime receives the whole effective environment so the SDK can refresh workload and subscription credentials itself. Because importing the SDK does not run Pi's CLI bootstrap, the SDK host explicitly establishes both upstream markers: generic agent attribution `AI_AGENT=pi` and Pi coding-agent detection `PI_CODING_AGENT=true`. Built-in Bash, extensions, and direct Shell Turns inherit both. Atomic writes use tmp+rename and chmod 0600.
- **Login**: `/login` queries the active session's public `ModelRuntime` for provider and interactive method metadata, then dispatches an owner-bound `loginProvider` intent. The SDK host revalidates project trust plus the live provider/method immediately before `ModelRuntime.login()` and supplies Pi-Vis's stable persisted device ID for 1.0.0 ChatGPT sign-in. Its app-owned interaction surface supports OAuth URLs, device codes, progress/info, text/manual/select prompts, and password-style API-key input. For the pinned Pi headless OpenRouter flow, a preceding authorization URL and its instructions remain available when the same login advances to `manual_code`, so the user can still open the browser while entering a returned code or redirect URL. Prompt values remain short-lived UI responses and never enter Zustand, authority outcomes, replay baselines, or logs. Provider errors are sanitized. Successful runtime login writes through Pi's credential store and triggers the silent model-catalog refresh/readback path. Pi may throw `CredentialSynchronizationError` after the credential commit; that partial success keeps the secret inside the host, publishes a dedicated “saved, refresh failed” warning, and lets the owner-bound readback/retry path recover instead of falsely reporting that sign-in failed. Runtimes without the public login capability retain the embedded xterm.js terminal fallback.
- **Pi 1.0 auth UX**: The same `auth_url` plus `manual_code` interaction supports Anthropic's copy-code flow for a browser on another machine; the URL and instructions remain visible while the code or redirect value is requested. Login and logout choices derive public `isSubscription` metadata: subscription-backed OAuth is labeled **Subscription**, ordinary OAuth (including Radius) is labeled **Account**, and API-key methods remain **API key**. Pi-Vis does not infer those labels from provider IDs.
- **Radius MCP post-login setup**: Pi-Vis does not instantiate upstream `InteractiveMode`, so after a successful Radius OAuth login the app explicitly offers the equivalent optional global MCP setup. The consent prompt names `<agentDir>/mcp.json`; cancel means decline and never rolls back the committed credential. On consent, the SDK host locks and rereads only that global file, preserves top-level data and the existing file mode, updates a matching Radius server or selects the first free deterministic name from `radius`, `radius-mcp`, and `radius-mcp-N`, installs provider auth, removes conflicting OAuth from the target, and writes by exclusive same-directory temporary file, `fsync`, and atomic rename (`0600` for a new file). Malformed input fails closed. The intent returns only a bounded setup status, and only `configured` asks the renderer to dispatch the ordinary `/reload` against the exact original runtime owner. Stale-owner or refused reload leaves the config for the next user reload. Project-local MCP files remain deny-by-default and untouched.
- **UI response ingress**: Main strict-parses every renderer `ExtensionUiResponse` before registry routing. Response `id` and optional `operationId` are bounded to 128 UTF-8 bytes, text `value` to 64 KiB, and unknown object keys are rejected. Existing owner, renderer-generation, host, epoch, operation, and pending-request checks then fence the parsed response. This same bounded seam carries short-lived API-key and manual-code values without persisting them in renderer state.
- **Model catalog refresh**: Pi 1.0.0 refresh returns `{ aborted, errors }` rather than using rejection alone. A refresh intent completes successfully only when it was not aborted and has no provider errors; the host never clones the provider-keyed `Error` map across IPC. The renderer performs its separate owner-fenced catalog read only after that terminal success, so a partial refresh preserves the prior cache and exposes retry. Virtual-model selection and the routed physical model remain distinct runtime fields. Public auth/catalog signals and runtime-creation timeouts bound work where Pi supports cancellation.
- **Extension APIs**: Pi 1.0.0 extensions may register display-only Markdown transformers. The renderer batches visible user, assistant, and thinking text through an exact-owner `transform_markdown` read before rendering, while the SDK host keeps the extension functions private and returns only transformed strings. Context includes message type, streaming state, and measured width. Failures fall back to the current text, and transformed output never replaces raw authority events, persisted JSONL, history, or model context. The host also inherits `pi.sendUserMessage(..., { expandPromptTemplates: true })` through the public extension runner; no Pi-Vis command parser emulates template, skill, or command expansion. Transcript-aware system/tool changes, context edits, turn boundaries, nested tool calls, and image/classifier model calls likewise remain on public runtime surfaces.
- **Codemode image generation**: Pi 1.0's public codemode factory supplies the leaner prompt and `models.generateImages()` backed by `ModelRegistry.generateImages()`. Generated images use the session's runtime-resolved credentials; their usage counts toward session cost, and `image(block)` attaches validated base64 image parts to the result. Pi-Vis keeps model invocation and nested calls upstream-owned while its typed tool-result, authority snapshot, JSONL replay, and transcript image paths preserve the resulting ordered content. It does not reproduce codemode's prompt, close-match diagnostics, or argument validation.
- **Pinned pi runtime**: Pi-Vis bundles exact `@earendil-works/pi-coding-agent@1.0.0` and never detects or updates a pi binary on the user's machine—upstream ships breaking SDK changes in patch releases, so the runtime only changes with a Pi-Vis release (audit `docs/compatibility/` first). `src/main/pi/pinned-pi.ts` verifies the package manifest and resolves both its modular `dist/cli.js` SDK anchor (`path`) and published `dist/bundle/cli.js` executable (`cliPath`); only real CLI subprocesses use the latter, because the SDK host derives `dist/index.js` from the modular anchor. The persisted `settings.piBinaryPath` value is ignored unless the process explicitly sets the test-only `PIVIS_TEST_ALLOW_PI_BINARY_OVERRIDE=1` seam; repository E2E launchers opt in, while packaged verification clears it and proves an existing override cannot displace the bundle. The app never exposes a pi self-update target. The SDK host otherwise uses public Pi imports, with the single exact-version exception in [ADR 0006](../decisions/0006-pinned-llama-private-extension-exception.md): the isolated adapter selects Pi 1.0.0's `llama.cpp` factory from its shipped aggregate built-in registry and immediately returns to the public inline-extension and runtime APIs. Pi-Vis extension panels deliberately use public `TuiMainScreen` because their content-hugging ANSI replay protocol is not a `TuiAltScreen` viewport. Two packaging constraints (both bit in practice): Electron's patched `fs` makes `existsSync` succeed for paths inside `app.asar`, so the resolver must remap any asar hit to the `app.asar.unpacked` mirror before a child consumes it; and electron-builder re-hoists pi's shrinkwrapped nested `node_modules` to top level at package time, so `electron-builder.yml` asarUnpacks **all** of `node_modules/**` (renderer deps are vite-bundled into `out/`; the packaged `node_modules` exists only for subprocesses/native modules) and the host's `resolvePiDependency` searches ancestor `node_modules` dirs instead of assuming the nested layout. Packaged-app resolution cannot be covered by repository-tree tests—`npm run dist` spawns the published unpacked bundle, validates coding-agent plus the seven exact Pi dependencies and both entry paths, imports the exact private llama adapter, and runs the packaged PTY/Electron journey.
- **Agent-core boundary**: Pi 1.0 removed its harness, node, durable/session-storage, sessions/runtime, pico3, search/template/skill/system-prompt/telemetry schema, `uuidv7`, and pi-telemetry reexport surfaces. Pi-Vis never consumed them. Do not add `@earendil-works/pi-durable` to recreate those removed harness APIs; app authority, durability, replay, and search remain independent of agent-core.
- **Pi built-ins and MCP**: The host creates codemode, tool-search, and MCP through their public 1.0.0 factories with `{ builtin: true, replaceable: true }`, then composes them with the one audited llama factory through public `resourceLoaderOptions.extensionFactories`. ResourceLoader owns `builtin:<name>`, disabling/replacement, MCP configuration/transports/OAuth/provider auth, server ranking/search/namespace description, and reload discovery of newly added default tools. Project trust remains deny-by-default. Apart from the narrow, consented global Radius write above, Pi-Vis does not interpret MCP configuration, copy credentials into its protocol, or run a second `pi mcp` subprocess.
- **MCP OAuth and deferred tools**: Pi 1.0's public MCP stack owns `oauth.authServerMetadataUrl`, RFC 9207 authorization-response issuer validation, credentials isolated by server name and URL (including migration of a legacy URL-only record to its first server), normalization of empty optional OAuth fields, and step-up login that preserves already granted scopes. Pi-Vis neither interprets nor serializes those secrets. Pi also persists tool declarations and ResourceLoader owns definition registration plus reconnect ordering. The public SDK factory path supplies an initial default loadout, which bypasses Pi's constructor-time transcript restoration, so the host composes one hidden `pi-vis-transcript-tool-restoration` extension. On a non-reload `session_start` it derives the current declaration names from public `SessionManager.buildSessionContext()`, activates definitions already present through public `setActiveTools()`, and retains unavailable names only in memory. Before the next agent run it adds names whose MCP definitions have reconnected and abandons unresolved names at that prompt boundary, matching Pi's native behavior; removing a restored active tool cancels the pending restore. Pi's own ResourceLoader carries the current and pending loadout across `/reload`, so the bridge deliberately does nothing for that reason. The app stores no second durable MCP loadout and sends none of this state over IPC.
- **Pi-TUI settings**: The host reads `getShowHardwareCursor()`, `getClearOnShrink()`, and `getTerminalCapabilityOverrides()` from public `SettingsManager` on every runtime factory invocation. Both Unified and standalone `TuiMainScreen` constructors receive the resolved cursor flag and agent log directory and immediately call `setClearOnShrink()`; public `setCapabilityOverrides()` is reapplied on rebind. Pi 1.0's consolidated terminal-color/theme APIs remain upstream-owned; app chrome continues to use semantic Pi-Vis theme tokens. Upstream's fullscreen-by-default `InteractiveMode` and `quietStartup: "header"` affect only standalone CLI presentation: Pi-Vis constructs neither surface and retains content-hugging embedded `TuiMainScreen` panels plus app-owned startup chrome.
- **Pi tool defaults**: The SDK host does not pass an explicit built-in tool list to `createAgentSessionFromServices()`, so Pi 1.0.0's global/project `defaultTools` setting owns initial built-in selection, including `+`/`-` edits and the optional Windows `powershell` tool. Pi's public resource/session composition still adds extension and SDK custom tools; selecting defaults must not drop them, and `/reload` picks up newly added defaults. Strict-prefer schemas for Pi's built-in tools are now the upstream default; Pi-Vis does not duplicate them or require `PI_EXPERIMENTAL`.
- **Pinned Pi upstream-fix and security gates**: Pi 0.84.4 incorporated the former local fixes for custom-message/tool-result adjacency, unterminated JSONL-tail repair, and indexed fragmented Mistral calls. The official Pi 1.0.0 tarball remains pristine: there is no Pi postinstall/prebuild patch or private-file hash contract. Its published shrinkwrap pins vulnerable `brace-expansion@5.0.9` even though minimatch accepts `^5.0.8`; the application root lock therefore deliberately omits Pi's `hasShrinkwrap` marker and records 5.0.12 as the authoritative compatible closure. `scripts/verify-pi-security-closure.mjs` fails closed on official tarball URL/integrity drift, a restored shrinkwrap marker, changed embedded 5.0.9 baseline, unsafe lock metadata, or any actual Pi → minimatch → brace resolution other than 5.0.12. Root postinstall and every read-only worktree preflight run it, while final-app verification repeats the actual resolution after electron-builder re-hoisting. Behavioral coverage remains mandatory in `tests/pinned-pi-upstream-fixes.test.mts` and `tests/e2e/real-sdk-regressions.spec.mts`, so a later runtime cannot regress those guarantees silently.
- **Runtime disposal**: Planned SDK-host retirement disconnects IPC before sending a signal. The child closes its send queue and shell resources, then awaits public `runtime.dispose()` so MCP stdio clients and extension-owned subprocesses can close. Pi's MCP close path may use 500 ms before TERM plus two seconds before hard kill, so the child fallback is four seconds and main waits 4.5 seconds before SIGTERM, then three seconds before SIGKILL. Registry callers await actual exit and asynchronous lock unlock before replacement, including a compensating unlock for acquisition that races shutdown; extension signal handlers therefore cannot turn normal disposal into a deterministic three-second SIGKILL/restart overlap. Electron `before-quit` also awaits one shared registry/search drain, with an 8.5-second last-resort app deadline beyond the complete host escalation budget.
- **Pi extension-package updates**: Separate from the pinned runtime and Pi-Vis app updates. A default-on, non-blocking launch check runs after 3s and respects `extensionUpdateCheckEnabled`; opening Settings also checks when no launch/previous result is cached, while the button always performs a fresh manual check. Main owns the cached status and a single-flight claim, so launch, Settings, and manual callers cannot duplicate one package-manager pass. Results publish through `extensionUpdates.status`, populate Settings with every installed user-scoped npm/git package plus its current/latest version, and add an update-only count to the Settings affordance. Checks use pi's public, best-effort `DefaultPackageManager.checkForAvailableUpdates()` in an environment-isolated worker, then enrich the installed catalog with package metadata and public npm/git commands; unavailable registry/remotes leave the latest version unknown instead of hiding the installed row. The worker creates `SettingsManager` with `projectTrusted: false`, so automatic checks never read or trust project-local package configuration. Mutations invoke the bundled CLI only as `pi update --extensions --no-approve` or `pi update --extension <source> --no-approve`; `--self` and `--all` are intentionally absent because the shipped pi runtime remains pinned. Main serializes mutations, and a timed-out CLI is terminated as a process tree so npm/git descendants cannot outlive the reported operation. IPC invokes are `extensionUpdates.status`, `extensionUpdates.check`, and `extensionUpdates.run`.
- **Pi-Vis app updates**: Separate from extension-package updates and from the pinned pi runtime. `src/main/app-updates.ts` uses Electron's built-in `autoUpdater` only for packaged macOS builds (`app.isPackaged`, `darwin`, not `PIVIS_DISABLE_APP_UPDATES=1`). The feed defaults to `https://update.electronjs.org/rsingapuri/pi-vis/${process.platform}-${process.arch}/${app.getVersion()}` and can be overridden with `PIVIS_APP_UPDATE_FEED_URL` for diagnostics. Background check runs at launch after 5s and respects `appUpdateCheckEnabled`. IPC channels are `appUpdate.status`, `appUpdate.check`, and `appUpdate.install`; events are emitted as `appUpdate.status`. When Squirrel.Mac reports `update-downloaded`, the renderer shows a restart-to-install prompt and calls `autoUpdater.quitAndInstall()` through `appUpdate.install`.
- **Renderer navigation**: BrowserWindow consumes Cmd/Ctrl+R and Cmd/Ctrl+Shift+R at `before-input-event`; Chromium refresh is not a supported lifecycle because it destroys generation-fenced renderer custody while SDK hosts continue running. Session `/reload` remains the explicit runtime reload path.
- **Dependencies**: Electron 43 publishes its installer as `install.js`/`install-electron` but no longer declares a package install lifecycle; importing `electron` lazily installs it. Pi-Vis's root `postinstall` therefore runs that shipped installer synchronously once and verifies the installed version, safe relative executable path, and binary before any parallel test/build worker can import Electron. It next verifies the read-only Pi security closure above, then applies the sole repository-owned dependency patch to exact `@homebridge/node-pty-prebuilt-multiarch@0.14.0` (native, externalized from main bundle, asarUnpack in electron-builder). Every standard dev/test/build command also runs the read-only `ensure-worktree-dev` preflight: a local install or same-lock sibling `node_modules` link is usable only when both Electron and the Pi security closure pass before reuse and after new-link creation; an install made with `--ignore-scripts` fails actionably instead of triggering Electron's lazy extractor or accepting stale transitive bytes. The node-pty helper-path rewrites match complete `app.asar` / `node_modules.asar` path components so the plain-Node SDK host's already-unpacked path is not rewritten to `app.asar.unpacked.unpacked`. The patch remains exact-hunk and fail-closed, `prebuild` fails on version/content drift, and `verify:packaged-pty` exercises both the unpacked system-Node host resolution and Electron's logical-asar main resolution from the final app. That verifier also reads the packaged Electron framework's `CFBundleVersion`, requires an exact lock match at or above 43.5.0, and resolves the safe Pi transitive from the packaged layout without launching the GUI. The node-pty rewrite remains a bounded compatibility patch pending migration to a maintained PTY package; do not widen it into a generic dependency patcher. Other dependencies are `@xterm/xterm` + `@xterm/addon-fit` (renderer); `@xterm/xterm` + exact-version `@xterm/addon-serialize` (SDK-host Shell Turn emulation/keyframes); and `proper-lockfile` + `@types/proper-lockfile` (main).
