# Command system

The composer parses `!text` as bash, `/command [args]` as a slash command, and other input as a user submission. Slash matching is character-exact at the first position; leading-whitespace text such as `  /tmp/file` remains an ordinary prompt. That raw-editor decision is carried as the typed submission `inputKind` before file paths, diff comments, or images transform the transported prompt. The host validates the classification against the exact revision-matched raw editor before custody or Pi admission; a legacy request without the field is classified from that same raw snapshot. The validated value—not `text.startsWith("/")` on transformed text—controls slash image stripping, extension/queue semantics, Pi command/template expansion, and authoritative attachment clearing. Built-ins and discovered extension/prompt/skill commands are resolved by the SDK host. Built-ins take precedence over discovered-name collisions, matching autocomplete; discovered commands may still handle non-built-in names, including unsupported TUI-name collisions. `execute.ts` routes runtime-backed mutations through typed `session.dispatchIntent` envelopes and read-only lookups through `session.query`; the `submit` intent is the sole text-and-image transport path. Diff comments and file/image attachments are staged prompt context: every slash command receives only its command text, clears only that text after acknowledged execution, and leaves the staged context for a later ordinary prompt. This also applies to extension/template/skill and unknown slash commands that travel through the submit intent; the host defensively strips slash-command images and preserves authoritative editor attachments. An accepted ordinary submission clears the exact staged attachments and disables Pi's slash expansion even when prepending an absolute file path makes its transported text begin with `/`.

An extension may explicitly call public
`sendUserMessage(..., { expandPromptTemplates: true })`; in that path Pi owns
command, skill, and prompt-template expansion before admission. Pi-Vis does not
duplicate expansion logic or infer it from transported text.

`/model [search]` and `/thinking [search]` are app-owned searchable selectors.
An exact thinking argument is matched case-insensitively against the live
available levels and otherwise reports that authoritative list. Enter applies
the selected model or thinking level only to the current session; Ctrl+S sends
the same typed intent with `persist: true`, which delegates default persistence
to public `AgentSession.setModel()` or `setThinkingLevel()`. Pi's supported root
SDK does not expose InteractiveMode's configurable keybinding manager, so the
React picker uses Pi's literal cross-platform default Ctrl+S and does not import
the private manager or claim configured-binding parity. An intent receipt is
admission rather than successful persistence: repeated activation is fenced,
failed admission leaves the picker open, and only authority outcomes/readback
may report terminal failure or update canonical state.

## Direct Shell Turns

Shell-draft interpretation is a pure function of raw editor text. Only a position-zero `!` is special: `!cmd` is context-included, `!!cmd` is context-excluded, `!!!foo` runs `!foo` as excluded, and ` !cmd` is an ordinary prompt. The one- or two-character prefix remains editable text; there is no persistent shell-mode flag. The command suffix is trimmed only at submission. Composer blocks bare `!`, bare `!!`, and whitespace-only suffixes with a transient denial ring and no visible helper copy, while paste and Shift+Enter remain editing operations. The prefix replaces the attachment affordance and staged attachment UI is suppressed, not cleared, until ordinary Composer mode returns. A Shell Turn consumes only command text, so staged comments, files, and images remain attached to the editor for a later ordinary prompt. Composer measures normalized commands as UTF-8 and reports the 64 KiB limit only when exceeded; the hostile child boundary independently rejects an oversized bypass as `invalid/payload_too_large`.

`runBash` is an owner-bound stable intent containing the exact raw `editorText` and `editorRevision` from which its normalized command and `!`/`!!` classification were derived. It is admitted only while that revision and source still match child-authoritative editor state and the session is idle, has no pending Pi messages or submission/preflight custody, and has no competing foreground operation. The child validates those mutable facts in serialized ingress, starts public `emitUserBash()` preparation, releases the scheduler while the hook awaits, then re-enters serialized ingress to revalidate every fact immediately before execution and receipt publication. Busy, stale-editor, stale-owner, unavailable, transitioning, or pre-start-cancelled sessions return `not_admitted`; the draft is preserved and the command is never queued or replayed. Escape and legacy `abort_bash` fence a pending hook result even though the pinned Pi event has no `AbortSignal`; the stable route reports `cancelled`, and a late hook resolution or rejection cannot start, record, or persist a Shell Turn. The admitted receipt is withheld until the selected path's durable `pivis.shell_turn_start` marker and execution construction succeed: a handler result or replacement operations path is non-PTY, while only an unhandled event constructs the native PTY. A failure before that boundary returns `transport_unavailable` and creates no Shell Turn; a failure after the marker settles the admitted turn as failed. Composer clears only the matching local command revision after that receipt; newer edits and staged attachments remain untouched. Each session may own one Shell Turn, while separate live session hosts may each own one.

The SDK host first calls public `ExtensionRunner.emitUserBash()` exactly once, matching the pinned Pi RPC behavior. A handler-supplied full result is recorded directly without spawning, handler-supplied `BashOperations` run through public `AgentSession.executeBash()` as a non-PTY turn, and only an `undefined` result keeps the host-owned interactive PTY adapter. Pi 0.99.2 is fail-closed: a thrown handler or invalid defined result aborts instead of accidentally spawning. Every path uses the stable intent ID as the execution ID and retains one host-authored start/end lifecycle plus Pi's canonical Bash persistence. The bridge guards PTY and non-PTY paths as one foreground slot, including concurrent compatibility RPC requests. While replacement operations run, the host retains at most one MiB/512 chunks of ordered output for attach; the baseline's sequence watermark lets the renderer discard covered replay and append only later updates, and an omission notice remains visible until the canonical end replaces it. `!` leaves that canonical Bash execution message eligible for model context; Pi 0.99.2 represents both command and normalized output in the message. `!!` sets `excludeFromContext`, which excludes the entire canonical Bash message—not only output—while retaining the human-visible session record. It is not a sandbox, privacy, or project-trust control. On the default path raw PTY bytes drive the live Composer-bound terminal; only normalized settled output enters Pi's Bash result and the durable transcript.

## Submission contract

Before submitting, the renderer uses the current authoritative runtime snapshot and includes its host identity, session epoch, and editor revision. It also sends an intent id, requested queue mode (`steer` or `followUp`), surface (`composer` or `unified`), original `inputKind`, transformed text, and images. The host—not the composer—decides admission and returns a disposition. Current renderer requests always carry the explicit classification; the one-version compatibility path derives a missing value only from the revision-matched authoritative editor, never from transformed transport text.

The UI must not synthesize streaming, queue delivery, or prompt counters. `consumed` means Pi admitted the request; `in_custody` means it is retained behind a compaction/navigation barrier. A native pre-admission refusal may leave the still-visible draft untouched. Once a submission has visibly cleared, however, stale/rejected/unknown outcomes cannot put its text or attachments back. Direct snapshot queues replace visible pending messages. Queue-restoration records after ESC are acknowledged as non-replayable outcome evidence; `clearedIntentIds` permanently fence editor recovery.

The unified editor uses the same contract. Enter captures an immutable raw source revision plus frozen attachments, advances the authoritative editor to a new empty revision immediately, and emits a host→renderer request carrying the originating host/epoch identity. The pending source is dispatch custody only: it is never projected back into the current editor snapshot, so typing and a second Enter remain available while the first action settles. The renderer/main path validates that immutable source by stable intent, revision, and `inputKind` before any Pi side effect; transported text may differ because file paths, images, and diff comments are expanded later. The renderer generation must claim the whole unified action before execution. The claim has an unguessable ID and bounded deadline. Unclaimed requests may replay after reattachment; claimed requests never rerun, and acknowledgement loss or deadline expiry creates one non-replayable, dropped outcome record. Expired stable intents remain tombstoned, so replay or a late continuation cannot dispatch text twice. Success, guard bail, refusal, claim expiry, host loss, and renderer remount all retire custody without restoring the cleared source or disturbing a newer draft/attachment/comment revision. Editor patches remain revisioned, so a stale renderer cannot overwrite the host's canonical draft.

`/reload` has its own request and intent ids plus explicit `not_executed`, `completed`, or `outcome_unknown` settlement. Composer-originated reload intents also carry the exact editor revision and command text they may consume. The host clears only that unchanged command in the successor baseline; extension/picker reloads and newer/conflicted editor custody are preserved. A completed response names the acknowledged successor identity; Composer resynchronizes exactly that successor before clearing. It is refused while the authoritative snapshot is non-idle. `/tree` navigation uses the host's public in-memory tree API and is likewise protected from mid-turn mutation. `/share` carries the Composer/unified runtime identity and an export intent through its main-owned `gh` flow, so its `export_html` command cannot rebind after delayed auth work.

## Authority-frame intent migration

[ADR 0003](../decisions/0003-authority-frames-and-plane-synchronization.md) changes the target meaning of mutation dispatch without claiming that IPC can make Pi state instantaneous. In the target, every mutation is an owner-bound stable intent recorded by the child before possible Pi dispatch. The renderer may include the cursor it observed, but stale observation is context rather than a universal rejection rule; the child evaluates current authority state, while compare-and-set editor operations still require the exact revision.

An IPC receipt is only `admitted`, `duplicate`, `not_admitted`, or `delivery_unknown`. `refreshModels` is a stable mutation intent because public `modelRuntime.refresh()` mutates runtime catalog state; its terminal result is bounded (`refreshed`) and the catalog is read only afterward with an owner-fenced query. `loginProvider` is likewise stable and carries only provider id plus `oauth`/`api_key`; the child revalidates the runtime method and trust, drives public `ModelRuntime.login()`, and publishes no credential or provider-native error. `/login` gets its picker rows from the owner-bound `get_login_providers` query, never a Pi-Vis provider list. Neither receipt is command completion and components must not update canonical state from it. The child publishes typed completed/rejected/cancelled/failed/`outcome_unknown` outcomes in atomic authority frames. A same-owner duplicate with identical payload executes at most once; a reused ID with different payload is rejected. A possibly dispatched mutation whose settlement is lost becomes non-replayable `outcome_unknown` evidence and is never automatically replayed or reinserted after owner replacement.

Picker selections that continue `/fork`, `/models`, or `/logout` after the
source command has been cleared use the bounded `pickerAction` intent. It
carries only the selected entry, model-scope values, or provider; it cannot
carry arbitrary slash text or borrow the successor empty editor revision. Its
immutable originating surface is retained so extension lifecycle UI remains
owned by the Composer or Unified TUI that opened it. The child maps each typed
selection directly to its bounded app-owned built-in; discovered extensions,
prompt templates, and skills cannot shadow or intercept that continuation.
One synchronous fence belongs to each picker request across keyboard and
pointer activation. It is released only after a proven `not_admitted`/rejected
result, never after unknown delivery or settlement.

`!` and `!!` use the Direct Shell Turn path above. The child brackets Pi 0.99.2's correlated Bash lifecycle with one live turn (PTY only for an unhandled `user_bash` event) and one settled user-authored transcript item. The terminal intent outcome remains bounded operation evidence; it is not used as a second transcript authority.

`/trust` first reads the persistent post-start choice subset with the owner-bound `get_trust_state` query. A selection dispatches a `setTrust` intent containing only the exact child-produced option label. The child rebuilds the choices for the live cwd, rejects unavailable or session-only selections, and persists only the revalidated updates through public `ProjectTrustStore`. The picker waits for the typed terminal outcome, then dispatches reload with the latest same-owner observation only while the exact originating picker identity remains current; cancelling or replacing the picker permanently fences that continuation. The expected cursor advance caused by intent admission is not treated as a stale selection. Session-only trust remains available during initial resource resolution, where its runtime-only meaning can actually be honored.

The current `session.submit` dispositions and `session.sendCommand` settlements below remain the compatibility contract during phased migration. Existing intent requirements for effectful/replacement commands do not mean idempotent mutations have already moved to the target universal-intent protocol. Bridge legacy and frame paths only at an explicit authority baseline; do not merge a promise response, transcript event, and snapshot into a purportedly single current state.

## Command admission and settlement

Every renderer-originated non-text command carries a request id and the complete runtime identity that produced it. Effectful and replacement commands also carry an intent id. `SessionRegistry` is the sole admission authority and returns one of three correlated settlements:

- `not_executed` — the command did not cross child IPC (unavailable/transitioning/closing runtime, stale identity, or dispatch failure);
- `completed` — the active SDK host returned a terminal response, including a domain failure such as `Nothing to compact`;
- `outcome_unknown` — an effectful command crossed child IPC but its acknowledgement was lost.

A recognized command may clear after a matching `completed` domain failure because Pi consumed the command, but tests must not call that operation successful. `not_executed` and `outcome_unknown` preserve Composer/unified editor custody. An unknown effect is never replayed automatically: main retains its intent and publishes an interrupted-command review marker, retired only by explicit acknowledgement.

`PI_COMMAND_POLICY` in `src/shared/pi-protocol/commands.ts` exhaustively classifies every `PiRpcCommand` as read-only, idempotent explicit-state, effectful, or replacement. Text command discriminants remain submission-only. Main-owned read probes use a separate read-only API and are identity-bound; renderer command requests are never queued across activation or replacement. The host rejects ordinary command ingress once transition starts and refuses replacement while another command or submission remains active. Main rechecks the expected epoch after every non-replacement response; a response crossing an epoch boundary cannot settle as predecessor `completed` and effectful work becomes review-required unknown.
